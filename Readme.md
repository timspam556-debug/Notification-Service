# Notification Service
## Pet Project — .NET Backend Engineering

### 1. Описание проекта

**Notification Service** — backend-сервис для асинхронной обработки, управления и доставки уведомлений пользователям.

Основная задача проекта — разработать надёжную систему, которая принимает запросы на отправку сообщений, сохраняет их, помещает в очередь обработки и доставляет получателям в фоновом режиме.

Сервис должен поддерживать большое количество входящих запросов, не блокировать основные HTTP-процессы во время отправки уведомлений и корректно обрабатывать ошибки доставки.

Проект ориентирован на изучение и применение современных подходов к backend-разработке на C# и платформе .NET.

### 2. Практический сценарий

Представим, что существует интернет-банк или другая информационная система, которой необходимо отправлять пользователям уведомления.

Например:
- Подтверждение регистрации.
- Уведомление о новом входе в аккаунт.
- Информация об изменении состояния заказа.
- Уведомление о совершённой операции.
- Системные сообщения.

Вместо того чтобы каждая система самостоятельно реализовывала отправку уведомлений, она обращается к единому Notification Service.

Пример работы:

1. Внешнее приложение отправляет HTTP-запрос в Notification Service.
2. API проверяет данные и сохраняет уведомление в PostgreSQL.
3. Запрос на обработку помещается в RabbitMQ.
4. Фоновый Worker получает сообщение из очереди.
5. Worker определяет способ доставки и отправляет уведомление.
6. Результат доставки сохраняется в базе данных.
7. Если отправка не удалась, система повторяет попытку.
8. После исчерпания допустимого количества попыток уведомление получает статус Failed.

Таким образом, основное приложение не зависит от скорости работы внешнего сервиса доставки.

### 4. Архитектура системы

Проект будет состоять из нескольких логических компонентов.

**1. API Service**

Отвечает за:
- Приём HTTP-запросов.
- Валидацию входящих данных.
- Создание уведомлений.
- Сохранение данных.
- Возврат информации о статусе обработки.

**2. Message Broker (RabbitMQ)**

Отвечает за:
- Приём сообщений от API.
- Хранение сообщений до обработки.
- Передачу сообщений Worker-компонентам.
- Повторную доставку сообщений при временных ошибках.
- Направление окончательно не обработанных сообщений в Dead Letter Queue.

**3. Background Worker**

Отдельный фоновый процесс, который:
- Получает задачи из RabbitMQ.
- Обрабатывает уведомления.
- Вызывает соответствующий механизм доставки.
- Сохраняет результаты.
- Обрабатывает исключения.
- Управляет повторными попытками.

**4. PostgreSQL**

Хранит:
- Информацию об уведомлениях.
- Получателей.
- Содержимое сообщений.
- Статусы доставки.
- Историю попыток отправки.
- События Outbox.

**5. Redis**

Используется для:
- Кеширования часто используемых данных.
- Ограничения количества запросов (Rate Limiting).
- Уменьшения нагрузки на основную базу данных.

**6. Notification Provider**

Отвечает за фактическую отправку уведомлений.

На первом этапе реализуем Email Provider с использованием SMTP и Mailpit. В дальнейшем архитектуру можно расширить поддержкой Telegram и других каналов доставки.

### 5. Функциональные требования

#### 5.1. Управление уведомлениями

Необходимо реализовать:
- Создание уведомления.
- Получение уведомления по ID.
- Получение списка уведомлений.
- Фильтрацию по статусу.
- Фильтрацию по получателю.
- Пагинацию.
- Получение истории попыток доставки.

#### 5.2. Асинхронная обработка

Отправка уведомлений не должна выполняться непосредственно в HTTP-запросе.

После создания уведомление передаётся в RabbitMQ, а его дальнейшая обработка выполняется отдельным Worker.

#### 5.3. Статусы уведомлений

Предусмотреть следующие состояния:

- Pending — уведомление создано.
- Queued — помещено в очередь.
- Processing — находится в обработке.
- Sent — успешно отправлено.
- Failed — доставка окончательно завершилась ошибкой.

Необходимо корректно реализовать переходы между состояниями.

#### 5.4. Retry Mechanism

При временных ошибках доставки система должна автоматически повторять попытки.

Предусмотреть:
- Ограничение количества попыток.
- Экспоненциальную задержку между попытками.
- Сохранение информации об ошибках.
- Dead Letter Queue для окончательно не обработанных сообщений.

#### 5.5. Idempotency

Система должна защищаться от повторной обработки одинаковых запросов.

Для этого необходимо реализовать Idempotency Key.

Если клиент повторно отправляет запрос с тем же ключом, сервис не должен создавать дубликат уведомления.

#### 5.6. Надёжность данных

Реализовать Transactional Outbox Pattern.

Он необходим для решения проблемы согласованности между сохранением уведомления в PostgreSQL и публикацией сообщения в RabbitMQ.

Создание уведомления и соответствующего события Outbox должно происходить в одной транзакции базы данных.

Отдельный процесс будет публиковать события Outbox в RabbitMQ.

Также необходимо учитывать возможность повторной доставки сообщений и обеспечивать идемпотентность обработки на стороне Worker.

### 6. Пример API

Предусмотреть следующие endpoints:

**Создание уведомления**
POST /api/notifications

Пример запроса:

```json
{
  "recipient": "user@example.com",
  "subject": "Account notification",
  "message": "Your account has been updated.",
  "channel": "Email"
}
```

Ответ — ID созданного уведомления и текущий статус.

**Получение уведомления**

GET /api/notifications/{id}

**Получение списка уведомлений**

GET /api/notifications

**Фильтрация по статусу**

GET /api/notifications?status=Failed

**Получение истории доставки**

GET /api/notifications/{id}/attempts

**Повторная отправка**

POST /api/notifications/{id}/retry

Все ответы должны иметь корректные HTTP-коды и единообразную структуру ошибок.
